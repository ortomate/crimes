# orchestrator

## Friction log — orchestrator (round setup + cross-repo observations)

### `packs_loaded` reports what was loaded, not what ran
- **repo:** improbable (TS/TSX only, zero `.py` files)
- **command:** `crimes scan . --all --format json --no-init`
- **what happened:** `coverage.packs_loaded` = `["universal", "language-js", "language-py"]`
  on a repo with no Python whatsoever.
- **why it matters:** the protocol's own robustness advice is "check
  `packs_loaded`, don't just count findings" — but the field cannot
  distinguish *loaded* from *ran* from *found nothing*. A user debugging
  "why did the Python pack find nothing in my Python repo" gets no signal
  from the one field that is supposed to answer that. A `packs_used` or a
  per-pack file count would.
- **severity:** real problem

### `evidence` conflates code evidence with score arithmetic
- **repo:** improbable
- **command:** `crimes scan . --all --format json --no-init`
- **what happened:** `swallowed_error` evidence entries include
  `"confidence 0.78 = 0.72 base + 0.06 (protected operation touches external request)"`
  and `"severity raised by: external request"` in the same array as genuine
  code evidence like `"calls inside the protected region: fetch, res.json"`.
- **why it matters:** `evidence` is documented as the receipts for the
  finding. Score derivation is meta *about* the finding, not evidence *for*
  it. Any consumer that wants to render or reason over the evidence has to
  string-match to filter it out — which is exactly what this round's card
  builder had to do. A separate `score_rationale` field would keep
  `evidence` meaning one thing. Note this is a schema change, so it costs a
  minor bump.
- **severity:** annoyance (but a schema-shaped one, so cheaper to fix now
  than later)

### `crimes` is not installable as a global for testing without publishing
- **repo:** n/a
- **command:** `which crimes`
- **what happened:** no global binary; the round needed a hand-written
  shim pointing at `packages/cli/dist/index.js`.
- **why it matters:** minor for this round, but it means every
  "try it on your repo" instinct requires either `npx crimes` (network) or
  a build. Worth confirming `npx crimes@latest scan` is genuinely the
  frictionless path the docs claim, since that is the documented first-run
  command.
- **severity:** annoyance

### `--all` is a byte-for-byte no-op in `--format json`
- **repo:** hono, p-limit (verified on both)
- **command:** `crimes scan . --all --format json` vs `crimes scan . --format json`
- **what happened:** identical MD5. `hono` both `b8cac7b8813aed91268c77d3593b2d21`;
  `p-limit` both `ae256124a5331c55529fbbfe6c0fbfcf`.
- **why it matters:** `--all` is the documented way to opt out of "signal over
  exhaustiveness", and the dogfooding protocol itself (and `docs/`) tell users
  to pass `--all --format json`. In JSON mode the flag changes nothing. That is
  defensible as a design — JSON is the full contract, `--all` only affects the
  human renderer — but it is not what the flag's name or the docs imply, and a
  user filtering on it will conclude their config is broken. Either document
  JSON as always-complete and warn when `--all` is passed redundantly, or make
  the default JSON view actually summarised.
- **severity:** real problem (documentation/contract clarity, not correctness)

### Control result: p-limit is not silent
- **repo:** p-limit (df47604), 8 files, ~200 lines of source
- **command:** `crimes scan . --format json`
- **what happened:** 10 findings — 0 high, 6 medium, 4 low. Types:
  `swallowed_error` x3, `boolean_naming_drift` x2, `large_function`,
  `return_shape_roulette`, `direct_date`, `large_file`, `unbounded_async_fanout`.
- **why it matters:** p-limit is a few hundred lines of exhaustively reviewed
  code by a maintainer known for minimalism. Ten findings is more than zero.
  The mitigating and genuinely good news is **0 high** — the tool declines to
  alarm. But `unbounded_async_fanout` firing on a library whose entire purpose
  is bounding concurrency deserves individual scrutiny, and `large_file` /
  `large_function` on an 8-file repo suggests thresholds that do not scale down.
- **severity:** real problem

### CONFIRMED BUG: `large_function` (Python pack) reports a size claim it just disproved
- **repo:** pydantic and zulip, found independently by two blind judges
- **source:** `packages/core/src/detectors/py/large-function.ts:75-108`
- **what happens:** the detector fires on EITHER `tooLong` (lines > threshold)
  OR `tooDeep` (nesting >= DEEP_NESTING). But the summary is built
  unconditionally as:
      `${fn.name}` is ${lines} lines[ and nests N levels deep]. At this size an
      agent must read the whole body before it can safely change any part of it.
  When a finding fires ONLY on nesting, the prose still leads with the line
  count and still says "At this size" — about a size that passed. Evidence
  line 83 then prints `14 lines (threshold 50 for shape "domain")` directly
  beneath it.
- **real examples:** pydantic `get_strict` — 14 lines, threshold 50, depth 4.
  `deep_update` — 9 lines. `flatten_errors` — 18 lines. zulip — 26, 19, 23 lines
  against a 50-line threshold.
- **why it matters:** the underlying finding (deep nesting) is legitimate. The
  message destroys it. Both blind judges independently classified these as
  self-contradicting and rated the detector noise — one wrote "the finding is
  really about nesting, and the size prose contradicts it". This is the single
  clearest case in the round of a **message bug being indistinguishable from a
  correctness bug** to the reader. `large_function` is the highest-volume
  detector in the corpus (2583 findings).
- **fix shape:** branch the summary on `tooLong` / `tooDeep`; lead with whichever
  actually tripped. Suppress or reword the sub-threshold evidence line.
- **severity:** blocker

### CONFIRMED BUG: `pass_through_abstraction` builds chains from name collisions
- **repo:** zulip (card zulip-0018)
- **what happens:** reported `get_services` "forwards through 5 layers across 5
  files". The actual body is one line: `return services.get(bot_id)`. The
  "chain" was assembled from unrelated `get` methods in `markdown_config`,
  `message_list` and `sub_store` — matching on the method NAME, not on a call
  path.
- **why it matters:** this is a correctness bug, not a calibration one. The
  finding asserts a specific structural claim that is simply false, with
  fabricated evidence naming five real files. `pass_through_abstraction` fired
  19 times, all in one repo.
- **severity:** blocker

### `sync_io_in_hotpath` has no working notion of "hotpath"
- **repos:** zulip, pydantic
- **what happens:** fires on code that is provably not a request path —
  a `if __name__ == "__main__"` setup CLI (zulip-0001), a Django management
  command `class Command(ZulipBaseCommand)` (zulip-0026), a `release/push.py`
  script (pydantic-0022), and an `@cache`-decorated once-per-process function
  (zulip-0039). Two more sit inside `if settings.DEVELOPMENT:` with a comment
  saying nginx serves the file in production (zulip-0009).
- **why it matters:** the detector's entire claim is about WHERE the I/O
  happens. 202 findings across 8 repos, and the "hotpath" half of the name is
  not being established at all.
- **severity:** real problem

### `boolean_naming_drift` flags names that cannot be renamed
- **repos:** zulip, pydantic
- **what happens:** four separate findings on `atomic = False` inside
  `class Migration(migrations.Migration)` — a Django-defined attribute name.
  Also 18 names "bound to a boolean expression with nothing saying they hold
  true/false" that are Pydantic fields explicitly declared `name: bool`.
  Also flags names its own convention clause exempts ("or an idiomatic bare
  name"): `nullable`, `plural`, `frozen`, `from_attributes`, `lock_acquired`.
- **why it matters:** 637 findings, third-highest volume in the corpus, and
  a large share target identifiers that are framework-owned (unrenameable),
  already type-annotated as bool, or explicitly exempted by the detector's own
  stated convention.
- **severity:** real problem

### `swallowed_error` does not read the comment that explains the catch
- **repos:** hono (20 of 43 cards), improbable, p-limit
- **what happens:** in nearly every case the code carries an explanatory
  comment or an immediately visible fallback. One judge noted the detector
  recognised deliberateness on exactly one card while missing an identical
  comment two functions above. Also fires where the next line is `throw err`
  (hono-0011) and where the catch calls three recovery functions (improbable).
- **why it matters:** 289 findings across 7 repos. It has a
  `BEST_EFFORT_FUNCTION_RE` recognition path, and the evidence suggests it is
  far too narrow.
- **severity:** real problem

### SYSTEMIC: detectors with OR-triggers print evidence for the condition that did NOT trip
- **repos:** pydantic, zulip, drf — found independently by three blind judges
- **the pattern:** a detector fires on `A || B`, but builds its summary and its
  leading evidence line from `A` unconditionally. When only `B` tripped, the
  finding presents a measurement that PASSED as though it were the reason,
  and the reader sees a self-refuting statement.
- **confirmed instances:**
  - `py/large-function.ts:75-108` — fires on `tooLong || tooDeep`, always says
    "is N lines … At this size". 12 of drf's 50 cards, plus pydantic and zulip.
  - `todo-density.ts:40` — `if (matches.length < 3 && density < threshold) return []`,
    i.e. fires on count>=3 OR density>threshold, then prints
    "4.2 markers per 1k LOC (threshold 10)".
- **why it matters:** this is the round's most damaging finding, because it is
  cheap to fix and expensive in trust. Every blind judge independently used the
  word "contradicted". A reader who catches the tool stating something its own
  evidence disproves stops believing the findings that ARE correct — and the
  underlying signals here (deep nesting, TODO count) are legitimate.
- **fix shape:** derive summary and evidence from whichever condition actually
  tripped. Audit every detector with a compound trigger for the same shape.
- **severity:** blocker

### `weak_test_signal` does not follow assertion helpers
- **repos:** drf (7 cards), zulip (3), pydantic (5)
- **what happens:** claims "N of M test functions assert nothing" where the tests
  delegate to a helper that asserts. drf-0033: 11 of 11 tests route through
  `_resolve_urlpatterns`, which the card itself prints asserting on three
  attributes. drf-0037: 10 tests call `_assert_datetime_rendering`, shown
  ending in `self.assertInHTML`. zulip-0004: tests call `_verify_archive_data`.
  Also counts `self.assert*` but not `self.fail`, and not
  `model_dump_json(warnings='error')`, and treats `@pytest.mark.benchmark`
  functions as assertion-free when measuring is their entire purpose.
- **why it matters:** 619 findings across 8 repos — 4th highest volume. Extract-
  a-shared-assertion-helper is one of the most common test idioms there is, and
  the detector reads it as the absence of testing. It is most wrong on exactly
  the well-factored suites it should be quietest about.
- **severity:** blocker

### Vendored and framework-owned code is treated as domain code
- **repos:** drf, zulip, pydantic
- **what happens:** drf-0007/0009/0036 target vendored minified
  google-code-prettify. 10 pydantic cards target `pydantic/v1/`, the frozen
  vendored v1 tree. drf-0014/0028 flag Django's own mandated package layout
  (`management/commands/*`) as reaching into internals. Django `Meta.abstract`,
  `Meta.proxy`, `Migration.atomic` flagged as badly-named.
- **why it matters:** `util/scope-class.ts` is documented as the single answer
  to generated/vendored/production classification. On real repos it is not
  catching vendored trees, framework-mandated layouts, or frozen legacy
  subtrees. This inflates every downstream count.
- **severity:** real problem

### VERIFIED BLOCKER: source under a dot-directory is silently skipped, and reported as clean
- **source:** `packages/core/src/discovery/files.ts:25` — `dot: false`, hardcoded,
  no config or CLI override anywhere in `discovery/`.
- **minimal repro (built and run by the orchestrator, not reported second-hand):**
  identical Python file, 8 lines, nesting depth 5, one `open()`.
    as `visible.py`               -> "2 findings across 1 file"
    as `.agents/skills/bad.py`    -> "No crimes detected. Suspiciously clean."  EXIT 0
- **found in the wild:** ebg keeps all 62 of its `.py` files under `.agents/`.
  `coverage.files_by_language` had NO `py` key, yet `packs_loaded` still listed
  `language-py`. An A/B against the same tree with `.agents` renamed to `agents`
  went from 759 findings to 967, and turned up a real
  `cross_language_concept_alias_drift` that the real scan reported as zero.
- **why it matters:** this is the worst failure mode a scanner can have — a
  confident all-clear on code it never opened, with a cheerful message and a
  zero exit code. `.agents/`, `.github/`, `.claude/`, `.server/`, `.config/`
  are all common. Nothing in the output hints that anything was skipped.
- **severity:** blocker

### VERIFIED BLOCKER: `crimes context` ids do not resolve in `crimes explain`
- **repro (orchestrator-run, repo `improbable`):**
    $ crimes context src/MetricsGrid.tsx     -> id=crime_00001 (a MetricsGrid finding)
    $ crimes explain crime_00001             -> file: src/server/migrations.ts
  A different file. `context` numbers its findings locally from 1; `explain`
  resolves against the global scan ordering. They only agree when the file
  happens to rank first.
- **why it matters:** `context <file>` then `explain <id>` is the documented
  pre-edit agent workflow and the core of the agent-native positioning — the
  `crimes` skill and `crimes init --agents` both point at it. An agent following
  it gets a confident, detailed rationale for a finding in a different file,
  with exit 0 and no warning. Independently found on ebg and reproduced here.
- **severity:** blocker

### `cross_language_route_drift` can only ever see a Python backend
- **source:** `packages/core/src/detectors/cross/route-drift.ts:124` — skips any
  file whose `pack !== "language-py"`.
- **consequence:** a TypeScript backend is structurally invisible to it. ebg has
  22 `app/api/**/route.ts` handlers exporting 23 verbs against 9 client
  `fetch("/api/…")` sites — a textbook drift surface — and the detector cannot
  produce a finding on it in principle, not by calibration.
- **why it matters:** combined with the corpus-wide zero, the 0.15 release's
  headline detector has (a) never fired on real code and (b) excludes the most
  common polyglot shape in the JS ecosystem.
- **severity:** blocker

### `agent_risk` has collapsed into size — a stated product invariant
- **repo:** ebg (measured), consistent with the corpus-wide ranking
- **what happens:** 15 of the top 20 findings by `agent_risk` are
  `large_function` / `large_file`. Nothing from the 0.16 slate appears, despite
  `parallel_destination` firing 52x and `orphaned_destination` 39x in that repo.
- **why it matters:** `CLAUDE.md` states `agent_risk` "is the differentiator and

- **severity:** blocker

### VERIFIED BLOCKER: the 0.17.0 fingerprint fix did not fix the bug class
- **claim under test:** v0.17.0 release notes — "Self-scan collisions: 3 -> 0",
  and "The bug is in the fingerprint function's inputs, so it gets one general
  answer" (the `discriminator` field).
- **what is actually true:** only **2** detector files set `discriminator`
  (`exact-duplicate-block.ts`, `magic-domain-literal-scatter.ts`). The general
  mechanism shipped; it was wired into the instances the self-scan happened to
  surface. At least four other detectors have the identical shape.
- **measured on real repos (orchestrator-verified from the scan JSON):**
  | repo | findings | unique fingerprints | lost to collisions |
  |---|---|---|---|
  | hono | 377 | 288 | **89 (24%)** |
  | zulip | 3759 | 3433 | **326** |
  | buildfest | 1556 | 1362 | **194 (12%)** |
  | pydantic | 578 | 552 | 26 |
  Worst groups: `weak_test_signal` x8 (empty symbol), `commented_out_code` x12
  (empty symbol), `large_function` x9 (`describe callback`),
  `duplicate_component_shape` x10.
- **why it matters:** these are exactly the consequences 0.17.0 named as its
  reason for a wire-format break. `crimes ignore` on one `commented_out_code`
  finding silently suppresses up to **12**. `crimes diff` is blind to 24% of
  hono's findings. The self-scan was a biased sample — this repo has few test
  files and little commented-out code — and the fix inherited that bias.
- **fix shape:** any detector that can emit more than one finding per
  (type, file, symbol) needs a discriminator. Empty `symbol` is the tell.
  Consider asserting uniqueness in the scan pipeline so this cannot regress.
- **severity:** blocker

### NOTE FOR ANYONE READING THE ARTIFACTS

### `docs_code_drift`: indented code fences are not recognised, so Python generics parse as markdown links
- **repo:** pydantic
- **finding:** `crime_00411`, `docs/concepts/models.md` — "16 local links … point at
  file(s) that do not exist on disk", with evidence
  `docs/concepts/models.md:731 → data=1 (not found)`,
  `:733 → data='value' (not found)`, `:735 → data='value' (not found)` …
- **root cause, traced to one regex:**
  `packages/core/src/ia/extract.ts:233` — `const FENCE_RE = /^```/;` — is
  **anchored to column 0**. pydantic's docs put fences inside mkdocs-material
  admonitions and tab blocks, so they are indented:
  `docs/concepts/models.md:715` is `    ```python {upgrade="skip"}`.
  `parseMarkdown` never enters fence state, so the whole code block is scanned
  as prose by
  `MD_LINK_RE = /\[([^\]]+)\]\(([^)\s]+)(?:\s+"[^"]*")?\)/g`.
- **and the collision is exact:** a Python generic subscript immediately
  followed by a call — `Response[int](data=1)` — is **character-for-character a
  markdown inline link** `[int](data=1)`. pydantic's docs are *about generics*,
  so this is maximally unlucky.
- **scale:** `grep -rnE '^[ \t]+```' docs/` = **246 indented fences** vs 1000
  column-0 fences in pydantic's docs. ~20% of the doc corpus is invisible to
  the fence tracker. Every generic example inside one is a candidate link.
- **fix shape:** allow up to 3 leading spaces per CommonMark (`/^ {0,3}```/`),
  and ideally track the opening fence's indent to find its close. Patch-level
  (detector tuning + eval re-run).
- **severity:** real problem

### Cross-language diagnosis — three independent structural misses, all confirmed by running the parsers directly
- **command:** custom probe over `packages/language-py/dist` + `packages/language-js/dist` on all 8,919 Zulip files
- **what happened:**
  - `PY ROUTES total = 0` across **2,016 Python files, 0 parse errors**.
  - `JS FETCHSITES total = 0` across all `.ts`.
  - `PY CLOSED SETS = 0`; `JS CLOSED SETS = 25`; **name matches = 0**.
- **causes, in order:**
  1. **Routes are only read from decorators.** `routeFromDecorator()` in `packages/language-py/src/parse/routes.ts` is the *sole* route source. Zulip declares **387** URLs as Django URLconf **function calls** — `rest_path("realm/domains", GET=…, POST=…)` and `path(…)` inside `v1_api_and_json_patterns` in `zproject/urls.py`. Repo-wide count of `@app.get`-shaped decorators: **0**. Django/Flask-`add_url_rule`/`urlpatterns` is the dominant Python web idiom and the extractor cannot see it at all.   2. Even if `path()` were parsed, `routeFromDecorator` rejects any path not starting with `/`. Every Zulip route is relative (`"realm"`, `"messages/<int:message_id>"`) because the prefix comes from `include()`. So a `path()` extractor would still need prefix composition to produce anything.

Receiver `channel` fails `REQUEST_RECEIVERS`; and the URL lives in an **object-literal first argument**, which `literalText()` returns `undefined` for. jQuery-`$.ajax({url})` / any options-bag HTTP wrapper is invisible. This is a very common shape.
  4. **`cross_language_type_drift` is structurally impossible here.** The TS half only accepts **string-literal** unions (25 found). The Python half only records a member value when the RHS is a **string** node. All 29 of Zulip's `Enum`/`IntEnum` classes use **integer** values (`MEMBERS_ONLY = 1`). String-enum-vs-string-union is a narrow slice of real Python.

## Notes on measurement conditions

Between 5 and 8 other `crimes` processes (other repos in the same
dogfooding round) were running concurrently on this 10-core box for the
whole duration of the PostHog scan. **All wall-clock timings below are
contaminated by CPU contention** and should be read as an upper bound,
not a clean measurement. Max RSS is less affected.

### `--no-init` is a global option but is not listed in `scan --help`
- **repo:** posthog
- **command:** `crimes scan --help`
- **what happened:** the protocol's canonical invocation is
  `crimes scan "$R" --all --format json --no-init`. `scan --help` lists 13
  options and `--no-init` is not among them. It only appears under
  `crimes --help` as a top-level option. First reaction was "this flag
  doesn't exist on scan" and I nearly dropped it.
- **why it matters:** the flag that every CI/agent invocation needs is
  invisible from the help of the command everyone actually runs.
- **severity:** annoyance

### `scan` on a 1.6M-LOC repo prints nothing for >10 minutes
- **repo:** posthog
- **command:** `crimes scan . --all --format json --no-init`
- **what happened:** no progress output of any kind. No file count, no
  "parsing 32k files", no spinner, nothing on stderr. For the first eight
  minutes the only way to tell it was alive was `ps`. RSS oscillated
  between 50 MB and 340 MB, so it was clearly working, but from the
  outside a hung process and a working one are indistinguishable.
- **why it matters:** the first thing a new user does is point it at
  their monorepo. If it looks hung for ten minutes they Ctrl-C and never
  come back. There is no `--verbose`, no `--progress`, no ETA.
- **severity:** real problem

### The scan spends most of its wall clock inside one `git log` subprocess
- **repo:** posthog
- **command:** `crimes scan . --all --format json --no-init`
- **what happened:** sampling the stuck-looking process showed the main
  thread blocked and one child:
  `git log --since=90 days ago --pretty=format:CRIMES_COMMIT %cI %ae --name-only --no-merges`
  That subprocess alone ran for >5 minutes. Run standalone the same
  command takes ~88 s and emits **138,253 lines** (PostHog's 90-day churn
  window). Git also warns
  `exhaustive rename detection was skipped due to too many files` — that
  warning goes to the subprocess's stderr and is swallowed; nothing
  appears in `crimes`' own stderr.
- **why it matters:** the churn window is a fixed 90 days with no config
  knob and no cap on output size. On any repo with PostHog's commit rate
  this dominates the scan. Node also has to buffer the whole 138k-line
  blob in memory before parsing it.
- **severity:** real problem

### Run 1 of the JSON scan: killed externally at 773 s, no partial output
- **repo:** posthog
- **command:** `/usr/bin/time -l crimes scan . --all --format json --no-init`
- **what happened:** `EXIT=143` (SIGTERM) after **773.52 s real**,
  164.29 s user, 51.67 s sys, **max RSS 678 MB / peak footprint 1.09 GB**.
  The SIGTERM came from outside crimes (a sibling dogfooding session
  running `pkill`), so this is *not* a crimes crash — but the consequence
  is: `posthog.json` was **0 bytes**. Thirteen minutes of work produced
  nothing at all, because the JSON reporter buffers the entire document
  and writes it in one go at the very end.
- **why it matters:** on a repo this size any interruption — Ctrl-C, CI
  step timeout, OOM killer — costs the whole run with zero salvage. There
  is no incremental/streaming output and no cache, so a retry starts from
  zero.
- **severity:** real problem

### `crimes scan` never completes on this repo — killed twice, 358s and 731s
- **repo:** ortomate-studio
- **command:** `crimes scan ~/dev/ortomate-studio --all --format json --no-init`
- **what happened:** Two independent runs. Run 1: SIGTERM at **358s real**,
  output file **0 bytes**. Run 2 (`/usr/bin/time -l`): SIGTERM at **731s real**,
  256s user, peak RSS **493 MB**, output file **0 bytes**. Non-deterministic
  wall clock, deterministic outcome: no JSON, ever. Exit 143 both times.
  Not an OOM — memory plateaus around 230–490 MB.
- **why it matters:** For a user this is indistinguishable from a hang. There is
  no progress output, no spinner, no per-file logging, and nothing on stderr.
  You stare at a blank terminal for 12 minutes and then have nothing. The JSON
  contract is "the product" per CLAUDE.md, and on this repo the product does not
  emit.
- **severity:** blocker

### Root cause: minified-bundle exclusion is name-based only (`**/*.min.js`)
- **repo:** ortomate-studio
- **command:** per-subtree bisect — `crimes scan <subdir> --format json --no-init`
- **what happened:** Bisected by subtree. `Sources/` (Swift, 6.1 MB) = **3s**.
  `server/` = **4s**. `ios/` = **1s**. `chrome-extension/` = **killed, never
  finishes**. That subtree holds `chrome-extension/reference/claude-1.0.77/assets/`
  — **92 of the repo's 95 tracked `.js` files**, 12 MB, **812 total lines**, with
  a single line of **1,621,186 characters**. These are Vite-hashed vendor bundles
  (`sidepanel-Bb4xbmwz.js`, `index-BYVE4JzA.js`, `mermaid.core-BAp6MO0B.js`).
  `DEFAULT_CONFIG.exclude` in `packages/core/src/config.ts` only has
  `**/*.min.js` and `**/*.generated.*` — pure filename patterns. Modern bundlers
  do not emit `.min.js`; they emit `name-HASH.js`. Nothing in the default path
  looks at file size or line length before handing the file to the parser.
- **why it matters:** Any repo that vendors a built frontend — extremely common —
  will hit this. The fix is cheap (bytes-per-line or max-file-size heuristic) but
  the failure mode is total.
- **severity:** blocker

### No CLI escape hatch for exclusions
- **repo:** ortomate-studio
- **command:** `crimes scan --help`
- **what happened:** `scan` has no `--exclude`, no `--max-file-size`, no
  `--timeout`. The only way to exclude the vendor bundles is to write
  `crimes.config.json` into the repo — which a read-only evaluator (or anyone
  auditing a repo they don't own) cannot do, and which `--no-init` explicitly
  exists to avoid.
- **why it matters:** When the tool chokes on a directory there is no way to get
  past it from the command line. Broken and unworkaroundable is worse than broken.
- **severity:** real problem

### Timing caveat for this round
- **repo:** ortomate-studio
- **what happened:** `ps` showed up to **8 concurrent `crimes scan` processes**
  from other agents in this dogfooding round on the same machine. All wall-clock
  numbers here are contended and should be treated as upper bounds. CPU% per
  process sat at 12–90%.
- **severity:** annoyance (measurement hygiene, not a tool defect)

### Corpus clone was broken on arrival (environment, not crimes)
- **repo:** drf
- **command:** `git -C ~/crimes-dogfood/corpus/drf status --short`
- **what happened:** The clone had an **empty git index** (0 files) and only 15
  files on disk — `rest_framework/` and `tests/` were entirely absent. Cause:
  `git-lfs` is not installed on this machine, and `git checkout` aborts the
  whole worktree write at `docs/theme/src/drf-logos.fig` (an LFS pointer):
  `git-lfs filter-process: git-lfs: command not found` … `fatal: smudge filter
  lfs failed`. The abort left the checkout half-done and the index blown away.
- **fix applied:** set `filter.lfs.{smudge,clean}=cat`, `filter.lfs.process=""`,
  `filter.lfs.required=false` in the clone's local config, then
  `git reset --hard <SHA>`. Restored 154 `.py` files.
- **why it matters:** Not a crimes bug, but a **corpus-integrity** one. Had I
  scanned as-received, crimes would have reported ~0 findings on a repo with
  0 source files and looked beautifully calibrated. Any dogfooding round needs
  a source-file count assertion before it trusts a low finding count.
- **severity:** blocker (for the round, until fixed)

### BLOCKER: `crimes scan` on a nonexistent path exits 0 and reports "Suspiciously clean"
- **repo:** drf (reproduces anywhere)
- **command:** `crimes scan ~/crimes-dogfood/corpus/drff --no-init`  ← note the typo
- **what happened:**
  ```
  CRIME SCENE REPORT
  repo: drff  ·  0 findings

  No crimes detected. Suspiciously clean.
  ```
  **Exit code 0.** Nothing on stderr. `--format json` is equally confident:
  `summary.total = 0`, `coverage.files_total = 0`, and
  `packs_loaded: ["universal","language-js","language-py"]` — a full,
  well-formed, apparently-successful report for a directory that does not exist.
  `crimes scan /no/such/path` behaves identically.
- **why it matters:** this is the most dangerous output the tool can produce,
  because it is indistinguishable from a genuine pass and it *praises* you for
  it. It fails in the direction of false confidence.
  - It would have silently absorbed the broken clone logged above: had I not
    counted `.py` files by hand first, drf would have scored "0 findings" and
    been written up as crimes' best control result of the round.
  - `coverage.files_total: 0` is the tell, but it is buried in JSON and absent
    from the human view entirely — the human renderer never prints how many
    files it looked at.
  - CI wrapping `crimes scan` as a gate passes green forever on a path typo,
    a moved directory, or a bad `--root`.
  - Note `~/crimes-dogfood/artifacts/zulip.json` and `ortomate-studio.json` are
    **0 bytes** from earlier sessions in this same round. Worth checking whether
    they are the same class of silent no-op.
- **contrast:** `crimes verdict --base <bad-ref>` and `crimes explain <bad-id>`
  both get this right — clear stderr message, **exit 2**. `scan` is the outlier.
- **fix shape:** error + non-zero exit when the root does not exist or is not a
  directory; and print `files scanned: N` in the human header so `0` is visible.
  Both patch-level.
- **severity:** blocker
